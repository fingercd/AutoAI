## 一、benchmark：先采用一个负担可控、但边界正确的协议

### 1. 不必一开始就做十次重复、十折交叉验证

你先做**单种子的交叉验证**，作为第一轮完整评测，我认为是合理的。关键不在于一开始重复多少次，而在于：**用于选择模型和参数的数据，与用于报告最终性能的数据，必须分开。**

我查到的 PMLBmini 小数据分类 benchmark，本身就采用分层三折评估，并对逻辑回归的超参数选择使用嵌套验证；它并不是“十次重复×十折”才成立。它的主指标是 AUC，这也说明不同 benchmark 会根据任务目标采用不同指标，没有唯一通用组合。:chatgpt-content-reference{index="0"}

我建议第一版分成两条评测路径：

| 数据集情况 | 第一版正式评测 | 模型、配方和超参数在哪里选择 |
|---|---|---|
| 已有合理的官方 Train/Test 划分 | 保留官方测试集，不额外套一层外层五折 | 仅在官方训练集内部做三折验证；开发试跑阶段可先用固定验证集 |
| 没有官方独立测试划分 | **单次外层五折交叉验证** | 每个外层训练集内部，再固定划出一份验证集，例如约 20% |
| 独立样本或少数类太少，五折不合理 | 按预先规定的规则降为三折，或采用适当的分组留出 | 仍保持选择数据与最终评测数据分离 |

第二行是我最推荐你先实现的折中：

**外层五折＋内层固定验证集，而不是外层五折×内层五折。**

它仍然把“选择方案”和“评价方案”分开，但没有让每个超参数候选再乘上五倍训练成本。与完整内层交叉验证相比，代价是选参结果可能更不稳定，后面可以在代表性任务上补强。模型选择与性能评价共用同一批验证结果，会产生偏乐观的估计；这个边界不能靠多换几个随机种子解决。:chatgpt-content-reference{index="1"}

还有两个执行细节需要一开始就确定：

**每个外层折都要重新运行整个选择过程。**不能先用全数据的摘要让 LLM 选好模型，再只对这个模型做五折。否则评价的是“已经看过完整数据后选出的模型”，不是你的完整系统。

**按真正独立的单位划分。**独立表格样本可用 `StratifiedKFold`；有重复光谱、同一患者多次测量等情况，优先采用适当的分组划分，如 `StratifiedGroupKFold`。若官方划分没有隔离相关样本，也不能因为“官方提供”就忽略，应另外标明采用了修正后的协议。:chatgpt-content-reference{index="2"}

### 2. 指标先定少而清楚，不要寻找一个包办所有问题的指标

对于当前的分类任务，我建议：

**主指标：Balanced Accuracy。辅助指标：Macro-F1、Accuracy。**

Balanced Accuracy 是各类别 Recall 的平均值，适合避免多数类完全主导结果；在通常的单标签分类定义下，它与 Macro-Recall 对应，不需要把两者当成两份独立证据。:chatgpt-content-reference{index="3"}

论文里真正重要的，不只是每个方法各有一个平均分，而是：

> **在相同数据划分上，你的方法相对基线提高多少，以及这种提高在多少个独立任务上成立。**

所以结果汇总建议包括：配对性能差、胜／平／负任务数、平均排名，以及成本。显著性比较可以采用跨数据集的配对方法，例如 Wilcoxon 检验并对多重比较进行校正；不要把五个折当成五个互相独立的数据集。:chatgpt-content-reference{index="4"}

对于重复测量数据，还要明确最终目标是“判断一条光谱”还是“判断一个样本”。若实际应用是后者，主结果最好也按样本汇总预测；平均概率或投票的规则提前固定，而不是看哪种汇总分数高再决定。

### 3. 稳定性实验可以后补，但子集要提前选

第一轮完成后，我建议在**预先选定的 20—30 个代表性任务**上做加强验证，例如增加两个划分种子，或把内层固定验证集改为三折。

这个子集按照样本量、类别数、维数和领域选，不按照“我们在哪些任务上表现好”选。

这样能把两个问题分开：

> 全任务第一轮回答“整体是否值得继续”；代表性加强实验回答“结论是否对划分敏感”。

而且，从已经得到的任务级配对差异计算区间，并不需要重新训练。不过，这种区间不能替代训练随机性和划分敏感性实验。

## 三、你提出的三类对比，我建议这样正式定义

你说的“每个模型跑一遍”，非常适合建立一个**可复用的实验结果矩阵**。但需要区分三种东西：

**随机选一个模型、把所有模型跑完再选一个、事后查看哪个模型的测试分数最高。**

它们对应不同能力，也消耗不同预算。

### 1. 先建立四个核心实验组

第一阶段先固定预处理，避免模型选择、预处理选择和超参搜索同时变化。每个任务只使用事先确定的合法模型集合。

| 编号 | 如何选模型 | 超参数处理 | 回答的问题 |
|---|---|---|---|
| **R0** | 均匀随机选择一个合法模型 | 固定默认参数 | 没有数据相关选择时的起点 |
| **A0** | LLM 选择一个模型 | 同样的固定默认参数 | LLM 的模型选择本身是否有效 |
| **R1** | 均匀随机选择一个合法模型 | 执行统一规定的 HPO | 有调参能力，但模型随机选，会怎样 |
| **A1** | LLM 选择一个模型／配方 | 与 R1 完全相同的 HPO | 调参条件相同时，LLM 是否仍选得更好 |

最先关注的两个差值就是：

\[
\Delta_{\text{默认参数}}=A0-R0
\]

\[
\Delta_{\text{开启搜索}}=A1-R1
\]

**这两组对比最直接对应你的初衷。**它们不会把“后台搜索的收益”误记成“LLM 选择的收益”。

这里还有一个值得保留的基线：**在开发任务上确定的最佳固定模型**。例如开发结果显示某个模型普遍较稳，就将它固定用于所有评测任务。否则，超过随机选择还不能说明系统比“永远用一个不错的模型”更有价值。

### 2. “随机选择”不需要真的反复训练很多次

对某个固定划分，如果有 \(M\) 个合法模型，而且每个模型的结果已经计算出来，那么均匀随机选模型的期望分数就是：

\[
\mathbb E[S_{\text{随机}}]
=\frac{1}{M}\sum_{m=1}^{M}S_m
\]

因此，你想做的：

> 每个模型用默认参数跑一次，每个模型开启搜索再跑一次。

正好可以生成 R0、R1 的结果库，不需要为了随机 baseline 另外再训练几十次。

如果要模拟“不同外层折分别随机选模型”，可以从缓存的预测中抽取和组合，再重新计算指标，依旧不需要重新训练。对于 Macro-F1 这类非线性指标，应该重新汇总预测计算，而不是随意平均一些不对应的分数。

但要保留一个边界：

**结果库属于离线评测器，不属于 LLM 的输入。**LLM 做选择时，不能看见所有候选在该测试任务上的隐藏结果。

### 3. “所有模型跑完再选最好”也可以比较，但单独列

建议增加两个参考组：

**Portfolio-Default：**所有模型用默认参数训练，依据内层验证结果选择一个。

**Portfolio-HPO：**所有模型分别调参，再依据内层验证结果选择一个。

它们有助于回答：

> LLM 只训练少量方案，能否接近大量试验后选择的效果？

但是 Portfolio-HPO 的实际成本大约与模型数乘搜索预算有关，不能当作和“只选择一个模型”的同预算基线。

至于“事后用测试分数挑出的最好模型”，可以作为描述性的参考上限，观察还有多少可改善空间，但不能作为一个实际可部署的选模方法。

### 4. 主流 HPO：先确定两个必做，一个选做

我的具体建议是：

| 方法 | 优先级 | 在你的实验里怎么用 |
|---|---|---|
| **Random Search** | 必做 | 与其他方法共享搜索空间和预算 |
| **Optuna TPE** | 必做 | 作为根据已观察结果选择后续参数的 HPO 基线 |
| **SMAC3** | 第二阶段选做 | 适合进一步比较包含模型类别和条件超参数的联合搜索 |

TPE 和 SMAC 都有成熟实现；SMAC 对含类别变量、条件结构的超参数空间尤其相关。:chatgpt-content-reference{index="11"}

这里最好分两项实验：

**第一项：固定模型，比较调参方法。**
同一个 SVM 或随机森林，分别用现有搜索、Random Search、TPE，比较在相同预算下的结果。

**第二项：联合选择模型和参数。**
搜索空间包含 `model_id` 及该模型对应的超参数，比较 LLM 配方选择与非 LLM 联合搜索。模型类别选择加上其条件超参数，通常称为联合算法选择与超参数优化。

这两项不要混在一起：前者检验搜索器，后者才检验整体建模方案选择。

### 5. 搜索预算先小，但要避免两个很具体的陷阱

第一轮我建议先看 **1、3、6 个候选配置**的预算曲线，默认配置计入预算。空间较大的模型，后面再增加更高预算的对比。

**陷阱一：六次 TPE，可能实际上全是随机搜索。**

例如 Optuna 4.6 的 `TPESampler` 默认 `n_startup_trials=10`，前期采用随机采样。只给六次 trial 而不调整，就没有真正测试到 TPE 的后续采样阶段。低预算实验可以明确设定较小的启动次数，如两次或三次，并对所有方法说明共同的初始化规则。:chatgpt-content-reference{index="12"}

**陷阱二：候选空间已经全部跑完，就很难再比较搜索算法。**

你当前有限搜索域中，有些模型只有很少的候选。若所有方法都枚举完相同配置，最终结果接近是正常的，区别主要在前几个候选的顺序和达到较好结果的成本。现有搜索计划确实是在有限候选中执行。

因此，当前可以先研究**有限预算下的选择效率**。后续需要比较更一般的 HPO，再统一扩展搜索空间，而不是只给某一个对手更大的空间。

另外，第一版要确认“不搜索”确实没有隐藏搜索；不同方法共享相同训练器、早停规则和最终重训规则。比较搜索器时，也要统一其优化目标，不能一组按验证 Balanced Accuracy 选优，另一组换了目标，再把差异全部归因于搜索算法。

## 四、怎样控制实验量，并检查 LLM 请求是否真正有效？

### 1. 先估算拟合次数，再决定全量配置

举一个纯预算示例：

假设有 100 个任务、13 个模型、外层五折，每个模型六个候选，默认配置包含在六个候选中，那么仅候选拟合就是：

\[
100\times13\times5\times6=39,000
\]

如果每个候选再做内层三折，就变成 117,000 次拟合，还没算最终重训。

这不是你的实际耗时估计，但说明你的工作量担忧确实需要在设计阶段处理。

我建议采取三个节省办法：**默认配置复用、相同配置复用、随机选择基线使用缓存结果**。相同配置的判定要包括数据划分、预处理、参数、训练种子和执行版本，不能仅凭模型名称相同就复用。

缓存节省的是研究计算成本；论文报告部署成本时，仍应计入该方法本来需要执行的训练，不能因为这次命中缓存就报告为零成本。

### 2. 第一轮 LLM 验收重点不是“它选中了唯一正确答案”

选哪个模型通常没有一个事先确定的唯一正确答案。功能正确性与策略有效性，需要分开检查。

| 阶段 | 功能上确认什么 | 效果上评价什么 |
|---|---|---|
| 选择请求 | 输出合法；实际执行的模型、参数、预处理与接受的提案一致 | 相对 R0、R1 和固定模型是否有提升 |
| 诊断请求 | 使用真实训练／验证证据；没有改写数值、虚构问题 | 后续是否帮助产生更有效的调整 |
| 结束／总结请求 | 正确绑定运行结果；选择只依据允许的验证信息 | 结果是否清楚、可核查 |
| 记忆更新请求 | 只修改允许的记忆区域；来源可追踪；满足容量上限 | 后续未见任务的决策是否改善 |

你当前主线仍是单 Run，诊断不触发第二次训练，所以先把前三步验收清楚，再接后续行动，是与现有结构吻合的。

我同意你不必把“失败”做成现阶段的大课题。**把失败、重试、超时和人工介入自动记录下来即可；如果确实为零，就如实报告。**

现阶段更值得检查的反而是“不报错但没有真正生效”：例如声称关闭 HPO，后台仍然搜索；LLM 返回了某个参数，最终执行却用回默认值。这些会直接影响实验解释。

### 3. 全部 benchmark 可以跑，但先分清开发与最终评测

这里是最容易因为“先跑起来再说”而遗漏的一点：

**用于改提示词、改知识和改策略的任务，与最后检验效果的任务，最好提前分开。**

可以把现有已经反复分析过的任务主要放入开发／经验形成池，把新增的独立来源任务留作锁定评测池。所有任务的格式、接口、合法性检查都可以先跑；但最终测试分数不要一边看，一边用来修改系统。

这不是让你少做实验，而是避免后面已经完成大量计算，却无法清楚解释哪些结果是真正的独立评价。

## 五、你的分模型、固定容量记忆，建议先做这个版本

### 1. 先固定“每模型两条经验”，不要第一版就做复杂的多层知识网络

我会把它组织成下面几层：

| 层次 | 保存内容 | 如何使用 |
|---|---|---|
| **基础说明** | 模型用途、输入要求、实现支持的参数等相对稳定信息 | 简短常驻，不随单次实验改写 |
| **模型索引摘要** | 一句很短的适用性提示或检索入口 | 随模型目录展示 |
| **两条可更新经验** | 有条件的适用经验，以及限制／反例或另一类适用情境 | 初期固定读取，后期允许按需调用 |
| **证据引用** | 支持、反驳这条经验的实验记录编号和必要统计 | 需要时读取，不把全部历史放进 prompt |
| **通用经验** | 跨模型的验证、数据处理或预算经验 | 单独维护 |

这样你的想法不是“每个模型只有一句越来越模糊的话”，而是：

> **模型身份保持稳定，经验在固定槽位里精炼，证据仍然可追踪。**

这里还可以稍微调整一下层次理解：**抽象程度与读取深度不是同一件事。**上层通常是简短概括，往下展开的是更具体的条件和证据，而不是每往下一层都变得更空泛。

### 2. 固定条数之外，还要固定 token 预算

例如作为第一版配置：

> 13 个模型，每个模型两条可更新经验，每条最多 80 tokens。

那么核心经验正文的上限是 2,080 tokens。基础说明、索引和通用经验另外设上限，不混在一起计算。

你说的十几、二十个 token，很适合做索引；但要同时表达“适用条件、建议、限制”，通常需要更长一点的正文。具体长度用实际 tokenizer 测量，不靠中文字符数估算。

完整实验日志可以单独保留，用来复现研究；**不膨胀的是可供决策调用的记忆，不是把科研证据也不断覆盖掉。**

### 3. 更新请求只处理相关模型，而且允许“不更新”

你的更新逻辑可以直接落成：

```text
一次实验完成
    ↓
程序生成可信结果摘要
    ↓
取出被选模型的旧经验
    ↓
LLM 提出局部更新
    ↓
程序检查来源、字段、长度
    ↓
发布新版本，供后续任务使用
```

更新动作不必每次都重写。可以是：增强已有经验的支持、补充反例、缩小适用条件、替换较弱条目，或者保持不变。

**允许不更新很重要。**否则每次都要求“总结新经验”，容易把没有信息量的结果也变成一条看似深刻的规则。

ACE 对反复重写上下文导致信息丢失和内容逐渐失真的问题有专门讨论，其增量整理思路值得参考；它是记忆机制参考，而不是你的完整建模对比系统。:chatgpt-content-reference{index="15"}

### 4. 经验最好绑定“模型＋条件”，而不只是模型名称

例如下面只是结构示意，不是已经验证出的规则：

> 在某类高维、独立样本较少的数据条件下，模型 A 的某种预处理与参数范围值得优先尝试；现有支持来自哪些任务；在哪些任务中没有出现优势。

需要记录的条件，可以包含样本量区间、维数与样本量关系、类别不平衡、数据领域、预处理和预算。

这样你以后积累的不是“模型 A 好”，而是“模型 A 在什么条件下值得花一次训练预算”。

### 5. 只更新被选中的模型，会有一个可以提前处理的问题

若某个模型最初被选得较多，它就会获得更多经验，随后可能被选得更多；少选的模型一直缺少证据。

你前面打算建立的全模型结果矩阵，恰好可以用于**经验形成阶段**，让每个模型都有较均衡的初始证据。

但要把两种场景区分开：

**离线形成经验时，**可以使用经验来源任务上实际完成的多模型实验。

**在线处理新任务时，**只能根据实际执行过的试验更新，不能暗中把未执行的另外十二个模型的隐藏结果也交给它。

离线经验形成的成本另外报告，并说明需要服务多少后续任务才能摊薄。这会让“低成本”主张更加完整。

### 6. 记忆效果先做四组，不用一下子做十几种消融

| 组别 | 配置 |
|---|---|
| **M0** | 没有实验经验，保留共同的基础模型说明 |
| **M1** | 静态专家经验，不随实验更新 |
| **M2** | 相同 token 预算的扁平经验摘要 |
| **M3** | 你的分模型、分层、固定容量经验 |

M2 与 M3 使用相同来源的实验信息、相同容量预算，才能判断“分类组织和分层读取”是否有作用，而不只是因为 M3 看到了更多历史结果。

第一版先固定检索方式，把“记忆内容是否有效”测清楚。之后再比较固定读取和自主调用，避免同时改变记忆内容、读取策略和调用次数。

评测时先形成记忆，再冻结版本，在未见过的任务家族上测试。尤其不要让同一数据集前一个外层折的更新，直接传给后一个折——因为训练和测试样本会轮换，可能造成信息跨折流动。

你说的完整闭环可以成立。实验里只要再区分一句就足够：**实验后的记忆更新改善的是下一次决策；本次已经训练完成的模型不会因此自动变好。**

## 六、明确告诉你：Machine Learning Agent 对比先选哪几个

我建议主对比先固定三个，不要把所有相关系统同时复现。

| 系统 | 为什么选它 | 主要对应你哪个部分 |
|---|---|---|
| **DS-Agent，ICML 2024** | 基于案例推理完成自动数据科学，包含经验复用与反馈迭代 | 经验记忆和低成本选方案 |
| **MLZero，NeurIPS 2025** | 覆盖端到端机器学习自动化，使用多智能体和记忆机制；官方实现为 AutoGluon Assistant | 从输入到训练结果的完整流程 |
| **AutoML-Agent，ICML 2025** | 明确面向 full-pipeline AutoML，包含规划、实现与多阶段验证 | 任务理解、验证和流程组织 |

这三个不是单独的代码补全模型，而是面向整体数据科学／建模任务的系统。:chatgpt-content-reference{index="16"}

**SELA** 放在下一优先级：它的树搜索式建模探索，很适合你后续研究“诊断以后下一步试什么”，但第一轮不必四个一起接。:chatgpt-content-reference{index="17"}

执行上，我建议低成本的 R0/A0/R1/A1 覆盖全部合格评测任务；这三个外部 Agent 先在**事先选好的 20—30 个共同适配任务**上比较，再依据资源决定是否扩大。

比较要区分两种问题：

**机制对比：**同一个 LLM、同一套训练工具，比较固定工作流与反馈驱动决策。

**完整系统对比：**让外部 Agent 保留其原有方法，在相同任务、数据边界和计算预算下完成建模。

不要把外部 Agent 改造成只能返回你的一张配方，再称为原论文方法的完整复现。代码版本也要固定；例如 AutoGluon Assistant 的当前代码已包含论文发布后的更新，不能默认它等于原始 MLZero 实验版本。:chatgpt-content-reference{index="18"}

另外，仍建议保留一个完整的非 LLM AutoML 基线，以及适合任务的强预测器。光谱任务可参考 RamanBench 中的 ROCKET 或表格基础模型类别；它们不必全部加入你那十三个内部模型，但有助于判断外部竞争水平。:chatgpt-content-reference{index="19"}

## 七、怎样真正体现“小样本适配”，而不是只在小数据上跑一遍？

我建议专门保留一个规模不大的实验：

> 在同一批任务上，控制可用标注样本量，观察你的方法相对基线的优势如何变化。

例如，在数据允许且类别覆盖足够的前提下，比较 32、64、128、256 个独立样本，再加一个更大样本量或完整训练集作为参照。

这里的样本预算应包括**训练与验证所使用的全部标注样本**，不能说只有 32 个样本训练，实际上又用了大量额外验证标签来选方案。

这项实验能够回答比“我们的平均分提高了”更具体的问题：

**样本越少时，经验是否越有帮助？**
**样本很少时，多做 HPO 是否反而不稳定？**
**记忆能否在少试几个方案的情况下接近更大搜索预算？**

这些先作为待检验的问题，不提前写成结论。PMLBmini 也专门讨论了小数据中超参数选择困难、HPO 不一定带来稳定收益的情况，因此你提出的“默认参数与搜索参数同时比较”是有针对性的。:chatgpt-content-reference{index="22"}

还有一个很实用的判断：在开发结果矩阵里，检查是不是某一个固定模型已经在绝大多数任务上表现很好。如果确实如此，随机基线虽然容易超过，但选模的提升空间可能有限。此时更值得追求的可能是**达到相近质量所需的训练成本更低**，而不必硬把所有价值压在准确率提升上。

## 八、接下来按这个顺序走

| 阶段 | 主要工作 | 完成后应该拿到什么 |
|---|---|---|
| **第一步：冻结 benchmark v1** | 核对现有清单，补候选来源，标记独立任务家族，确定评测协议、指标和默认参数 | 一份可执行的任务清单和统一评测规则 |
| **第二步：开发任务试跑** | 先选约 10—20 个任务，跑全模型默认参数与小预算搜索，验收现有 LLM 请求 | 实际执行配置可信、成本可估算的结果矩阵 |
| **第三步：完成第一轮主比较** | 跑 R0/A0/R1/A1、固定模型及 Random Search/TPE；使用缓存减少重复计算 | 模型选择收益、搜索收益、成本和任务级差异 |
| **第四步：接入固定容量记忆** | 每模型两条经验，局部更新、版本冻结；完成 M0—M3 对比 | 记忆是否改善未见任务，以及压缩组织是否有独立价值 |
| **第五步：接上有限反馈行动** | 在总预算内允许追加少量实验，比较反馈决策与预定试验序列 | “反馈改变行动，并影响结果”的证据 |
| **第六步：补外部 Agent 与稳定性实验** | 三个主要 Agent、代表性任务额外种子、小样本量曲线 | 完整系统竞争力与结论稳定性 |

论文框架不必等全部跑完才开始。**问题定义、方法结构、benchmark 协议和消融问题，现在就可以同步写；结果和结论随着实验填入。**

关于“更 Agentic”，我会把它作为第五步的自然延伸：系统能根据证据决定**读取哪条经验、是否追加实验、下一步改什么、何时停止**，已经比增加聊天角色更直接。暂时不需要因此重做前端或追求不受约束的执行能力。

**总的来说，你现在最值得启动的不是另一个大模块，而是“开发任务上的全模型结果矩阵＋四组核心对比”。**它既能确认第一次 LLM 请求有没有选模价值，也能形成之后记忆模块需要的真实经验来源。这样 benchmark、决策、记忆和反馈是沿着同一批证据逐步建立起来的，不会变成几条互不相连、各自消耗大量实验的开发路线。
