## 一、先看结果：目前没有证明平均优势，但也没有证明显著劣于随机

独立重算得到：

| 比较 | 随机模型 BA | LLM 选模 BA | LLM 相对随机的差值 | 95% 家族 bootstrap 区间 |
|---|---:|---:|---:|---:|
| 默认参数：A0 对 R0 | 66.892% | 66.354% | **−0.538 个百分点** | [−3.014，+1.564] |
| 最多三套参数：A1 对 R1 | 68.886% | 68.756% | **−0.131 个百分点** | [−1.973，+1.640] |

这里是 **114 个正式任务的等权平均**，不是把 280 个轮次当成 280 个独立任务。两个区间都跨过零，因此准确表述是：

> **当前实现尚未显示出相对随机选模的稳定平均优势。**

不能直接写成“显著比随机差”，也不能因为差值小就认定两者等效。以上数字与原包汇总一致。:chatgpt-content-reference{index="5"}独立重算结果（历史引用：`sandbox:/mnt/data/autoai_review_outputs/recompute_metrics_output.json`）

### A1 比 A0 好，主要来自增加后台候选试验

这部分可以利用现有结果进一步拆开：

| 情况 | 平均 BA |
|---|---:|
| A0 选择的模型，使用默认参数 | 66.354% |
| **仍然使用 A0 选择的模型**，但允许最多三套参数 | **69.370%** |
| 改用 A1 选择的模型，允许最多三套参数 | 68.756% |

因此，这一轮的变化可以分解为：

\[
A1-A0
=
\underbrace{+3.016}_{\text{保留选模，增加参数候选}}
+
\underbrace{-0.614}_{\text{再切换到 A1 的选模}}
=
+2.402\text{ 个百分点}
\]

也就是说，**后台增加候选试验确实有收益；A1 重新选择模型，反而吃掉了其中一部分收益。**

这是基于已有预测做的顺序分解，不是新做的因果实验。但它已经说明：不能把 A1 高于 A0 全部归功于 LLM “更会调参”。:chatgpt-content-reference{index="6"}逐任务预算分解（历史引用：`sandbox:/mnt/data/autoai_review_outputs/budget_decomposition_recomputed.csv`）

## 三、这次新增的重点：验证时与测试时，不完全是在评价同一种预测

这是我认为应该优先于提示词优化核查的问题。

### 1. 源码中有两条不同的判类路径

训练侧的验证指标使用：

```python
pred = model.predict(x[indices])
balanced_accuracy_score(true, pred)
```

位置：`code/backend/app/training.py:424–439`。这些验证分数随后参与参数选优。

而 benchmark 的测试汇总使用：

```python
# 先将同一 Sample_ID 的概率平均
# 再取平均概率最大的类别
predicted = max(labels, key=lambda label: probabilities[str(label)])
```

位置：`code/backend/app/benchmark_driver.py:284–301`。

因此，存在两层差异。

**第一层：模型原生预测标签，不一定等于概率最大项。**

你这里的 SVM 使用 `SVC(probability=True)`。scikit-learn 官方文档明确说明，`predict()` 与 `predict_proba()` 的概率最大类别可能不一致。因此，**即使一个 Sample_ID 只有一条记录，benchmark 也可能把模型原生预测的类别改掉。**:chatgpt-content-reference{index="0"}

**第二层：验证按观测行计算，测试按样本组计算。**

有重复光谱时，“每条光谱分别判类再统计”与“先平均同一样本的概率，再判类”不是同一件事。即使每组重复次数相同，也不能认为两者等价。

源码位置和上下文已保留在:chatgpt-content-reference{index="10"}编号源码摘录（历史引用：`sandbox:/mnt/data/autoai_review_outputs/SOURCE_EXCERPTS.md`）中。

### 2. 已证实的是口径差异，不是它造成了多少损失

这里要谨慎区分：

> **已证实：选参数所依据的验证指标，与最终测试指标，没有完全相同的判类规则和评价单位。**

> **尚未证实：这个差异导致了 ToeSegmentation2 的低分，或者解释了 A0/A1 的整体负差。**

这也不意味着测试侧的“平均概率”一定错误。关键在于，你最终要交付的是哪一种预测，选优时是否与之匹配。

所以我不建议现在直接“把测试改成 `predict()`”。那样可能只是选择了一个在已见测试集上分数更高的规则，而不是解决评估设计问题。

### 3. 第一层检查可以不重训

训练代码已经把原生 `pred_label` 和 `prob_*` 同时写入原始 `predictions.csv`。读取已有文件，就能比较：

**原生标签与概率最大项的不一致率，以及这种差异如何改变混淆矩阵。**

本次压缩包没有完整的这些逐行预测文件，因此我没有计算实际影响量。证据包里的 `audit_saved_predictions.py` 就是用于这个只读检查的；它只在构造样例上测试过，**没有在你真实原始预测上运行**。

若要进一步判断是否改变了 HPO 的参数选择，还需要对应候选的 Valid 预测，不能仅凭最终 Test 预测推断。

## 四、候选顺序非常值得怀疑，而且不能只用“固定字母排序”解决

包内摘要已经指出顺序问题；我逐对检查后复现了这一现象，并核对了它如何产生。

### 1. 相同任务换预算时，候选排列也跟着变了

代码先给配方计算摘要，再按 `recipe_id` 排序；搜索计划参与摘要，因此预算改变会影响展示顺序。

280 对 A0/A1 请求中：

| 核对项 | 结果 |
|---|---:|
| 训练统计相同 | 280/280 |
| 默认参数映射相同 | 280/280 |
| 候选排列改变 | **280/280** |
| 最终选择模型改变 | **221/280** |

而且，这个顺序同时出现在 **user 消息的候选列表**和 **system 中 schema 的模型枚举**里。

### 2. 选择与位置的关联，比一般的“偏好常见模型”更明显

在 560 次正式选择中：

**262 次选择列表第一项，占 46.79%。**

**427 次选择 LR、SVM、Random Forest、XGBoost 四者中最早出现的一项，占 76.25%。**

更具体地，LR、RF、XGBoost 任意一个出现在首位的情况共有 **171 次，171 次都选中了它**。PCA-LDA 在首位时选中 31/60，非首位时只选中 1/500。:chatgpt-content-reference{index="11"}逐请求位置核对表（历史引用：`sandbox:/mnt/data/autoai_review_outputs/choice_position_recomputed.csv`）

这些事实足以把“位置依赖”列为高优先级假说，但还不能说已证明因果，因为现有预算对比还同时改变了其他内容。已有研究也发现 LLM 的多选行为会受选项排列影响，但那不能替代你这里的受控实验。:chatgpt-content-reference{index="1"}

**固定字母排序不是消除偏置。**它可能只是让同一个模型永远占据有利位置。先通过排列干预确认问题，再决定采用怎样的展示和决策机制。

## 五、第一次请求现在到底在做什么？固定 SVM 和三套参数又是谁决定的？

### 1. 本轮第一次请求，只选择模型，不提出超参数

实际约束是：

> LLM 返回一个 `model_id`，后台将其绑定到冻结配方和参数。

A1 虽然显示 `max_trials=3`，但没有把实际三套候选参数逐项展示给 LLM。因此，本轮检验的是：

**“LLM 在知道后台有有限搜索的情况下，能不能选好模型。”**

不是：

**“LLM 能不能生成比传统 HPO 更好的超参数。”**

### 2. 固定 SVM 是开发集选择出来的，不是 LLM 选出来的

程序在 15 个开发任务上，从共同合法的七种模型中，依据平均 BA 选择固定模型。两档预算都选中了线性 SVM，开发平均 BA 分别约为 **80.276% 和 79.995%**。

所以 F0/F1 的来源是合理的开发阶段选择，不是根据正式测试结果挑选。但 F1 固定的是模型类别，每个任务仍然会在允许的 C 值中按 Valid 选优。

位置：`benchmark_report.py:457–532`；冻结记录在 `results/formal-freeze.json`。相关内容见:chatgpt-content-reference{index="12"}完整报告第四节（历史引用：`sandbox:/mnt/data/Panda_Agent_首轮独立复盘_20261011.md`）。

### 3. 三套参数由后台固定表生成，不是随机搜索

常见执行次序是：

| 模型 | 参数候选 |
|---|---|
| LR | C：1 → 0.1 → 10 |
| 线性 SVM | C：1 → 0.1 → 10 |
| PLS-DA | 成分数：3 → 1 → 5 |
| PCA-LDA | 成分数通常为 3 → 10 → 30，按维数约束过滤 |
| Random Forest | 深度：3 → 5 → 10 |
| XGBoost | 深度：2 → 3 → 5 |
| 深度模型 | 学习率：0.001 → 0.0003 → 0.003 |

因此，目前“最多三套参数”更准确的名称是**后台固定候选搜索**，不是 LLM 调参，也不是随机搜索。

“最多”也确实有意义：PCA-LDA 在正式预算三的 280 轮中，有 75 轮实际只有一套合法配置。这不一定有问题，但不能把相同候选上限直接等同于相同训练成本。

### 4. 要改提示词，应改真正发送出去的那一层

这里有一个很具体、容易白忙的地方：

`BenchmarkLLMAdapter` 会在调用普通适配器后，**重写实际 system 和 user 消息**。

所以，仅修改普通 `agent_poc/orchestration/llm.py`，可能不会改变本轮 benchmark 的最终提示。

实际提示主要强调“选择合法动作”“返回 canonical model_id”“不要提交执行参数”“输出规定 JSON”。输入中有 Balanced Accuracy 字段，不能说完全没有性能目标，但**比较候选以争取更好的泛化性能，并没有被清楚地置于任务中心。**

同时，模型说明主要是版本号和候选数量；缺少有用的结构定义。输入也没有任务域、轴语义、候选试跑结果或 A1 完整参数候选。另一个已确认的展示问题是：实际请求仍写着 `8:1:1 holdout`，而真实冻结评测并不都采用这种划分。

这些可以说明**决策接口还有改进空间**，但仅凭目前短理由，也不能断定模型完全没有使用数据。详细请求与源码对照见:chatgpt-content-reference{index="13"}报告第四、六节（历史引用：`sandbox:/mnt/data/Panda_Agent_首轮独立复盘_20261011.md`）。

## 六、第二次请求目前没有实质决策空间；原始 JSON 合规性也要单独计数

### 1. 当前 Finalize 更像固定结束确认

本轮第二次请求只允许：

```json
{
  "tool_name": "finalize_ml_session",
  "arguments": {}
}
```

它不能更换模型、追加试验、改变参数，也没有真正的拒绝或重新规划分支。因此，虽然看到了验证信息，**它目前仍无法把这些信息转化为改变建模结果的行动。**

这不是说以后不需要验收请求，而是：**要让一次请求有价值，首先要明确它能决定什么。**

本轮 630 次 Finalize 消耗 241,375 tokens，占全部 LLM tokens 的 **17.69%**；累计请求等待占全部 LLM 请求等待之和的 **48.40%**。这不是整个训练平台能够加速 48.40%，训练成本需要另算。

近期可以把“确定性结束替代这次 LLM 调用”作为一个单独的协议简化提议；后续要做真正验收，再赋予有限的实际行动。不要静默修改本轮已经冻结的流程。:chatgpt-content-reference{index="14"}请求核对与用量摘要（历史引用：`sandbox:/mnt/data/autoai_review_outputs/independent_review_summary.json`）

### 2. 630 次选模原始回复，都经过了补括号

我读取原始响应后发现：

**630/630 次选模回复缺少最后一个外层 `}`；程序补齐后才接受。**

结束回复中，也有 209/630 次做了同样补齐。补齐没有改变模型选择值，绑定结果一致，所以目前不能把它解释成准确率下降的原因。

但它意味着：

> **流程成功率，与模型原始结构化输出的合规率，是两回事。**

日志中选择输出只有 35—57 tokens，`finish_reason` 都是 `stop`，不支持“用满 1024 tokens 导致截断”的解释。缺括号发生在模型生成、模板处理还是推理服务返回阶段，现有附件不能确定。

这件事值得查，但属于原始输出链的定点检查，不需要因此重跑训练。:chatgpt-content-reference{index="15"}原始响应核对摘要（历史引用：`sandbox:/mnt/data/autoai_review_outputs/independent_review_summary.json`）

## 七、下一步只做三个诊断，暂时不加 memory，也不扩大训练矩阵

### 第一优先级：核对预测与评价口径

先读已有 `predictions.csv`，对比原生标签、逐行概率最大项、逐组平均概率三种结果。重点检查 SVM，以及真正存在重复测量的任务。

**判断标准：**如果标签差异很小，就不继续把它当作主要解释；如果差异明显，再在开发数据上检查是否改变候选排序，并依据应用目标确定一致的规则。

这一步的首层比较不需要训练。若要改变选优或评测规则，则属于**科学协议修改**，要统一处理受影响的 A/R/F/P，而不能只换一种方法的分数。

### 第二优先级：只换顺序，做约四十次选择请求

从开发任务中按数据属性选四个已存上下文，例如两个有十三个候选、两个有七个候选。固定预算、统计、参数和其他提示内容，循环移动候选，让每个模型都占一次首位。

同时控制 user 列表和 system 枚举的顺序；加少量完全相同请求，检查服务本身的稳定性。**不触发训练，也不调用 Finalize。**

**判断标准：**如果相同输入重复时稳定，但只换排列就跟着首项或最早出现的常见模型切换，才能更明确地判断位置依赖。反之，如果模型身份基本稳定，就应降低“位置导致失利”这一解释的权重。

四个上下文只能用于机制筛查，不是完整的效能验证。

### 第三优先级：把“明确目标”和“增加客观信息”分开测试

先只明确目标：在合法候选中，选择预期未见样本 Balanced Accuracy 更好的模型，展示顺序不代表优先级。保持原输出结构。

然后另开版本，只补客观信息：真实 Train/Valid 规模、评价单位、可信的轴类型、模型结构定义，以及 A1 实际执行的参数候选。

**不要同时加入五张知识卡、历史赢家、memory 和思考模式。**否则即便分数提高，也难以知道是哪一项起作用。

判断应依据开发任务的选择结果、位置稳定性和成本，不是理由是否变长。只有这些因素控制后，再比较同样输入下的推理配置或更强模型，才更容易解释“模型能力”究竟是不是主要限制。
